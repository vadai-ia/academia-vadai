# M3 — Admin de cursos, módulos y lecciones

> **Estado: completo, listo para validación.** 17/17 aserciones en verde y la
> subida a Bunny verificada contra su API real.

---

## Cómo verificarlo

```bash
PORT=3117 pnpm start      # en una terminal
pnpm test:admin           # en otra
```

`test:admin` **ejecuta las server actions de verdad**. Cuando Next renderiza un
`<form action={serverAction}>` incluye un campo oculto `$ACTION_ID_<hash>`: es la
ruta de mejora progresiva, lo que hace que el formulario funcione sin JavaScript.
El script lee ese formulario del HTML y lo reenvía tal cual, así que corre
exactamente el mismo código que correría un navegador con JS apagado.

Eso además cierra el hueco que quedó abierto en M2, donde dije que las server
actions no se podían invocar por HTTP de forma estable. Sí se puede: el id está
en el HTML.

## Lo que se construyó

| Ruta | Qué es |
|---|---|
| `/admin/cursos` | Listado con estado, tipo, vigencia y conteos de módulos, lecciones e inscritos |
| `/admin/cursos/nuevo` | Alta de curso. Nace en borrador |
| `/admin/cursos/[id]` | Árbol de módulos y lecciones + datos del curso |
| `/admin/lecciones/[id]` | Editor de lección: tipo, estado, video, texto enriquecido y adjuntos |

### Decisiones que vale la pena conocer

**El árbol no necesita JavaScript.** Reordenar, borrar, crear y subir adjuntos
son `<form>` con su server action, sin envoltorios de cliente. §3.2 dice que
botones subir/bajar bastan para el MVP, y es la decisión correcta: drag & drop en
móvil es peor experiencia que dos botones, y además funciona si el JS falla.

> Los formularios de alta **no** cumplían esto al escribirse M3: envolvían la
> acción en una función de cliente para limpiar el campo, lo que rompe la ruta
> de mejora progresiva. Se corrigió durante M8 pasando la acción directa y
> reiniciando con `key`. Ver [M8.md](M8.md).

**Reordenar intercambia posiciones con el vecino**, no reindexa toda la lista.
Así el orden nunca queda con huecos ni con empates, y una sola operación toca dos
filas en vez de N. La prueba verifica justamente eso: que tras mover, las
posiciones sigan siendo únicas y no se pierda ningún módulo.

**El slug sigue al título hasta que lo tocas.** Una vez editado a mano deja de
moverse solo: cambiar el slug de un curso publicado rompe las URLs que ya andan
circulando.

**Las lecciones nacen en borrador.** Que una lección a medio escribir apareciera
sola ante los alumnos sería un default peor.

**Los cursos se archivan, no se borran.** `payments.course_id` es `on delete
restrict`: un curso con pagos registrados no se puede eliminar, y archivarlo
conserva el historial de quienes lo compraron.

**Tiptap persiste JSON, no HTML.** Así el render del alumno es controlado y no
hay forma de inyectar markup arbitrario. El JSON viaja en un input oculto, para
que el formulario siga siendo un `<form>` normal.

**Los adjuntos se descargan por URL firmada de 5 minutos.** El bucket es privado
(§4): no existe una URL permanente que alguien pueda copiar y repartir.

**Si falla el registro del adjunto, se borra el archivo subido.** Un archivo
huérfano en el bucket es menos grave que una fila apuntando a un archivo que no
existe, pero ninguna de las dos debería pasar.

**Tres barreras en cada acción.** Toda server action empieza por `exigirAdmin()`,
aunque el middleware ya filtró y RLS también protege. Una server action es un
endpoint público: nadie garantiza que la petición pasó por el middleware.

## Subida de video a Bunny ✅

Las credenciales llegaron y **la integración quedó verificada contra la API real**,
no solo escrita.

### Cómo funciona

El archivo va del **navegador directo a Bunny**, sin pasar por nuestro servidor.
Un video de 2 GB reventaría el límite de body de cualquier server action, y
además pagaríamos el ancho de banda dos veces.

Del servidor solo sale una firma con caducidad:

1. `prepararSubida()` crea el registro del video en Bunny y firma la subida.
   La `BUNNY_STREAM_API_KEY` entra en el hash pero **nunca se transmite**.
2. El navegador sube por **TUS resumible**. Si la conexión se cae a la mitad
   —muy probable subiendo 2 GB desde México— continúa donde se quedó en vez de
   empezar de cero. Es exactamente la mitigación que pide §11 para "upload de
   videos largos falla".
3. `confirmarSubida()` le pregunta a Bunny la duración y la guarda: la
   "duración auto-capturada" de §3.2.

El GUID se guarda **antes** de subir el archivo. Si la subida se corta, el video
ya existe en Bunny y se puede reanudar sin perder el vínculo con la lección.

### Qué se verificó contra la API real

```
✓ Acceso a la biblioteca
✓ Crear video               guid real, creado y borrado
✓ Handshake TUS con firma   201 aceptada
✓ Firma incorrecta          401 rechazada  ← prueba que Bunny SÍ valida
✓ CDN directo sin token     403 bloqueado
```

La tercera línea es la que importa: se firmó a propósito con los componentes en
orden invertido y Bunny lo rechazó. Eso descarta que el 201 anterior fuera un
falso positivo por no estar validando nada.

### ⚠️ Lo único que no pude verificar

**Que Token Authentication esté encendido en la biblioteca.** La configuración
vive en `api.bunny.net` y pide una llave de cuenta, no la de Stream.

Lo que observé sondeando: el CDN directo responde **403** sin token (bien), pero
la página del iframe responde **200** sin token. Como el video de prueba no tenía
contenido, eso **no es concluyente** en ninguna dirección.

Confírmalo a mano, porque es lo que impide que un alumno comparta la URL del
video y es la promesa de §0.B ("el contenido es el negocio"):

```
Bunny → Stream → tu Video Library → Security
  Enable Token Authentication = ON
```

`pnpm check:bunny` reporta lo que observa y te recuerda este paso.
